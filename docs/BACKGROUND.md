# Background: Agent ID, Agentic Wallet, and protocol concepts

This page is for developers who know how to use an EVM wallet and a DEX, but
have not used Agentic Protocol or Agentswap before. It explains the names and
roles that the rest of the documentation assumes.

## The pieces

| Name | What it is |
| --- | --- |
| **Agentic Protocol** | The on-chain protocol: gated token, transfer policy, identity adapter, registries, treasury, and Facility V2 templates. |
| **Agentswap** | The DEX product built on the protocol: gated Uniswap V3 pools, position manager, router, and quoter. |
| **Agentmarket** | The NFT venue built on the protocol: approval-based BNB listings and sales. |
| **Agentmarket CLI** | The terminal/MCP client for NFT collections and Agentmarket in the separate [Agentmarket CLI repository](https://github.com/agentic-labs-hq/agentmarket-cli). |
| **Agent ID** | An identity record issued through Binance's Agent ID system and bound to a BSC wallet. The protocol reads it through an adapter; the protocol does not issue it. |
| **Binance Agentic Wallet** | A non-custodial wallet operated through the Binance App and the `baw` CLI. It holds the wallet, signs, and applies the App confirmation flow. |
| **Agentswap CLI** | The terminal/MCP client for tokens and the DEX in the separate [Agentswap CLI repository](https://github.com/agentic-labs-hq/agentswap-cli). It builds and previews transactions through `baw`; it does not hold private keys. |
| **Facility** | A standard on-chain contract that can hold gated tokens without an Agent ID and expose a fixed set of project roles. |

A useful shorthand:

```text
Agentic Protocol = the rules and registries
Agentswap        = the DEX that uses those rules
Agentmarket      = the NFT venue that uses those rules
Agentswap CLI    = a tool for using Agentswap
Agentmarket CLI  = a tool for using Agentmarket
Agent ID         = the identity credential checked by the rules
Agentic Wallet   = the wallet that signs and confirms
```

## Agent ID

An Agent ID binds a handle to a wallet. The live BSC registry is external to
this project:

```text
0x60B9262456dE011F7d15a54CdD8c48bAaa8B022F
```

The protocol does not deploy or administer that registry. `AgenticIdAdapter`
performs three live reads for a wallet:

- the wallet has an Agent ID balance;
- the wallet has a non-empty handle;
- that handle resolves back to the same wallet.

If all three are true, the wallet is **eligible** (the code and CLI also use the
word **active**). There is no cached identity: eligibility is checked from live
registry state when the policy runs. If the registry call fails, the check fails
closed.

In this documentation, an **agent** is a wallet (or an operator controlling a
wallet) that passes the Agent ID check. It can be operated manually or by an
automated service; "Agent-only" is an eligibility rule, not a requirement that
the transaction be generated by an autonomous AI program.

An Agent ID is required to:

- receive gated tokens or a gated NFT;
- buy an NFT on Agentmarket under the canonical policy;
- own or operate a gated LP position;
- swap a gated asset;
- act as an agent-only facility role.

It is **not** required to:

- create a token or an NFT collection;
- create a pool (the caller must be the creator of every gated side);
- own a project facility;
- supply public quote assets to a gated pool, though such a supplier cannot
  receive gated output.

Use the matching doctor command to check the protocol's actual eligibility result
for the connected wallet:

```sh
agentswap doctor --json      # tokens and DEX
agentmarket doctor --json    # NFTs and Agentmarket
```

For claim status and the external account flow, use Binance's Agentic Wallet
tooling:

```sh
baw wallet agent-id --json
```

The Binance Agentic Wallet skill is the source of truth for its commands:
[binance-agentic-wallet/SKILL.md](https://github.com/binance/binance-skills-hub/blob/main/skills/binance-web3/binance-agentic-wallet/SKILL.md).

Do not confuse an Agent ID with a wallet address or with a `.ai` name used for
transfer resolution. The protocol checks the registry binding, not the display
name alone.

## Binance Agentic Wallet

The wallet is non-custodial and is controlled through the Binance App. The
`baw` CLI is the local command surface:

```sh
npm install -g @binance/agentic-wallet@1.12.0
baw auth signin --json
# complete the QR/verification flow in the App
baw wallet status --json       # must be CONNECTED
baw wallet address --json      # use the BSC address
baw wallet settings --json     # Developer Mode for contract calls
```

Developer Mode is required for `contract-call` previews and execution. The
Agentswap CLI uses the two-step preview/execute flow: `agentswap` builds calldata
and calls `baw contract-call preview`; after you inspect the result and confirm,
`agentswap tx execute --confirm` calls `baw contract-call execute`. The final
approval can still happen in the Binance App.

## Gated token and policy

A gated token is a fixed-supply ERC-20 whose transfer policy checks the sender
and recipient categories. The policy is set when the token is created and is
immutable for that token. It is not a generic allowlist that the project can
edit later.

The policy knows these categories:

```text
POOL, LP_MANAGER, FEE_RECIPIENT, CUSTODY, PURPOSE
```

A wallet that is not an agent can still be a token creator, a pool creator, or a
facility owner. What it cannot do is receive or hold gated assets, or
participate in gated swaps/LP, unless it controls an eligible Agent ID wallet.

## Facility: broad and narrow meanings

The word **facility** appears in two contexts:

- **Registry facility (broad):** any contract registered in the venue registry,
  including `POOL` and `LP_MANAGER`.
- **Project facility (narrow):** one of the five Facility V2 templates that a
  project deploys: `VAULT`, `LAUNCH`, `LOCKER`, `GAME`, `ESCROW`.

The facility guide is about the narrow project templates. A pool is a venue
facility, not one of the five project templates.

| Term | Meaning |
| --- | --- |
| **Category** | The policy/registry class: `CUSTODY`, `PURPOSE`, `POOL`, `LP_MANAGER`, `FEE_RECIPIENT`. |
| **Kind / type** | The `bytes32` label registered for a contract: `VAULT`, `LAUNCH`, `LOCKER`, `GAME`, `ESCROW`, or `POOL`. |
| **Subtype** | The same registry label when used to map a facility to its category; append-only. |
| **Venue** | A broad word for a registry member; it includes DEX pools and project facilities, not only DEX contracts. |

Concrete example:

- A pool created by `AgentswapPoolFactory` is registered with
  `facilityCategory = POOL` and `facilityType = keccak256("POOL")`.
- A VAULT is registered with `facilityCategory = CUSTODY` and
  `facilityType = keccak256("VAULT")`.

The registry answers "what kind of facility is this?" (`category`) and "which
template/type is it?" (`facilityType`). "Venue" is not a third registry; it is the
broad name for anything registered there.

## Roles at a glance

| Role | Agent ID required for this role? | Does the role itself grant holding? | Notes |
| --- | --- | --- | --- |
| Token creator | No | No | The caller becomes the creator. A creator that is separately eligible can also hold tokens. |
| Initial token recipient | Yes, or an active CUSTODY/PURPOSE facility | Yes, through the recipient check | Recipients are checked at creation. |
| Pool creator | No | No | Must be the creator of every gated side. |
| Swapper | Yes | Yes | Gated output goes to an eligible agent. |
| LP owner | Yes | Yes | Position manager checks owner, recipient, caller, and collect recipient. |
| Facility owner | No | No | Project EOA/multisig; ownership transfer is two-step. |
| Facility operator | Not necessarily | No | Only the roles marked agent-only in the facility guide. |
| Facility beneficiary | Usually yes for gated flows | Yes | See the per-kind rules; LAUNCH/LOCKER/ESCROW differ. |
| Protocol governance | No | No | 2-of-3 Safe; no Agent ID. |

Roles can overlap. A token creator, pool creator, or facility owner can also be
an eligible Agent ID wallet, and then it can hold gated assets **as a recipient
or participant**, not because of the creator/owner role.

This table is a map, not a replacement for the per-function rules in
[TOKEN_AND_POOL.md](TOKEN_AND_POOL.md) and [FACILITY_GUIDE.md](FACILITY_GUIDE.md).
